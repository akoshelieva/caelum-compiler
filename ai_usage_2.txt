5. TECHNICAL EXPLANATION OF CODE
------------------------------------------------------------------
The notes below provide concrete technical understanding to study and rewrite
in the student's own wording. They were themselves prepared with AI help.

- The lexer reads UTF-8 input, recognizes tokens with types and line/column
  positions, and rejects invalid characters early. It accepts both spellings
  of the cloud boolean type and maps them to one internal type token.
- The recursive-descent parser consumes those tokens and creates an AST. A
  separate precedence hierarchy ensures that * and / bind more tightly than
  + and -, and that comparison happens after arithmetic. The AST carries
  the information needed for later phases: source locations, arguments,
  parameter/return types, field names, and mutability flags.
- The semantic pass does not execute programs or emit LLVM. It constructs
  symbol records, resolves names by scope, verifies that types and argument
  counts agree, and checks when values/fields can be assigned. Registering
  function signatures before analyzing function bodies permits recursion
  and calls to functions declared below. Tracking mutating effects through
  calls is needed so a seemingly read-only method cannot write an astro
  field indirectly while called on a calm receiver.
- LLVM generation converts a semantically valid AST into the builder's
  instructions. Local storage uses alloca/load/store, conditions become
  conditional branches among basic blocks, and member access obtains the
  stored field pointer by struct index using GEP. Methods receive an extra
  pointer to the receiver. The generator declares scanf/printf and emits
  format strings as constants. Overflow/division guards branch to explicit
  runtime errors before performing unsafe operations.
- The test runner validates multiple independent properties: legacy AST
  compatibility, exact compiler error lines and lack of output files on
  failure, actual machine-code execution via Clang, exact stdout including
  newline characters, stdin fixtures, and runtime failures. End-to-end
  tests are necessary because valid-looking LLVM text can still have wrong
  runtime behavior or print the wrong integer width.
