4. HOW THE I UNDERSTAND THE CODE
--------------------------------------------------------
4.1 Piping: explain how x |> f |> g is parsed, how its types are checked,
    and what LLVM calls implement it.


Piping allows the result of one function to be passed to the next. The parser stores the sequence of functions in the AST. Then the compiler checks whether their types match and generates the function calls.


4.2 Unused-variable and unused-function elimination: explain how the
    optimizer detects unused declarations without deleting real side
    effects or confusing shadowed names.

The optimizer checks whether variables and functions are used. If a variable is not needed anywhere, it can be removed. It also takes scopes into account because variables can have the same names. Unused functions should also be removed.




4.3 Inlining: explain which one-use functions can be inlined, why local
    names are renamed, and why recursion/conditional returns are excluded.

Inlining replaces a function call with the function's code. This is done for simple functions that are called only once. Local variables are renamed to avoid name conflicts.



4.4 The interactive program: explain how Fire, Defend and EMP interact
    with energy, heat, shields and enemy actions; identify a specific
    expression in space_battle.txt where Piping is essential.

In the game, Fire uses 2 energy, deals damage to the enemy, and heats up the reactor. Defend protects the ship, restores energy, and reduces heat. EMP uses 3 energy, disables the enemy's shield, and makes the next attack stronger. The enemy can activate a shield, charge a laser, or attack more aggressively. Piping is used to calculate attack damage.



4.5 Testing and LLVM: explain what the .in/.expected sessions prove, why
    normal vs --optimize outputs must agree, and why llc/clang native
    execution matters beyond simply printing an AST or LLVM IR.

The `.in` files contain the player's actions, and the `.expected` files contain the expected game output. This helps check whether the program works correctly. I also compared the results with and without optimization because optimization should not change the program's behavior. With `llc` and `clang`, the game is compiled and run to check that the generated LLVM IR actually works.

6. MY UNDERSTANDING 
-------------------------------------------------

I chose Piping because I wanted to add a new feature while keeping as much of the syntax and functionality of the language from the previous stages as possible. Piping allows the result of one function to be passed to the next using `|>`. This means there is no need to nest function calls. In Space Battle, it is used to calculate attack damage depending on different conditions.

The optimizer includes three main transformations. Unused Variables removes variables that are never used, Unused Functions removes unnecessary functions, and Function Inlining replaces a function call with its code if the function is called only once and is suitable for this optimization.

Space Battle has a maximum of five rounds and three actions. Fire uses 2 energy and increases reactor heat by 3. Defend restores energy, cools down the reactor, and reduces incoming damage. EMP uses 3 energy, disables the enemy's shield, and makes the next attack stronger. The enemy reacts to the player's previous actions: it can activate a shield after several attacks or charge a stronger laser after repeated defending.

The test scenarios covered wins, losses, invalid actions, insufficient energy, and reactor overheating. I also ran the tests and compared the results.
